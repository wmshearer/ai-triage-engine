# Phase 2 — Agent Design Research: Structured Output & Multi-Agent Decomposition on a Local 7B Model

**Date:** 2026-08-18
**Scope:** Structured-output enforcement mechanism, quantization effect on schema adherence, whether four-agent decomposition is justified, realistic per-alert latency under `OLLAMA_NUM_PARALLEL=1`, and context-window constraints for 38-53-field alert records. Evaluation-harness metrics design, dashboard, and deployment are explicitly OUT of scope (separate briefs).
**Reads first:** `../wshearer-site/research/phase-0-architecture.md` (Phase 0 sketch: four agents — Enrichment, Triage, Correlation, Critic — plus Q1-Q4 runtime/model/structured-output/orchestration research) and `../wshearer-site/research/phase-0-metrics.md` (eval-corpus/sampling framing). This brief does not re-derive what Phase 0 already established correctly; it re-verifies the parts Phase 0 flagged as unconfirmed, corrects what's changed since 2026-08-17, and answers what Phase 0 never asked (concurrency-driven latency, decomposition justification with measured evidence).

---

## Verdict

- **Keep Ollama's native `format` JSON-Schema parameter as primary structured-output enforcement, but do not treat it as a semantic-correctness guarantee, and re-verify per-field before trusting an enum/technique-ID value.** Confirmed still current: Ollama 0.5.0+ (Dec 2024) compiles the schema into a grammar and constrains decoding via XGrammar, not retry-based. *(Confidence: high — primary source, unchanged from Phase 0's finding.)**
- **Do not adopt a four-agent sequential pipeline on the strength of the Phase 0 sketch alone — the classification/decomposition literature says a single well-prompted call is very likely to match or beat it on this task shape, at a fraction of the latency.** Multiple studies measuring decomposition vs. single-prompt on classification-style tasks found single-prompt equal or superior, at 2-12x lower cost. *(Confidence: medium-high — converging evidence from 3 independent papers, none of which test this exact alert-triage task, so extrapolation risk remains.)*
- **If agents are kept, budget ~15-40 seconds of pure LLM latency per alert on this hardware (4 sequential Q4_K_M calls, no parallelism possible) — full-corpus evaluation over thousands of alerts is not schedule-feasible without stratified sampling.** At an estimated 20-45 tok/s decode for a 7B Q4_K_M model on an 8GB card, 4 chained ~300-token-output calls plus per-call context loading puts single-alert latency in the same range as running the model itself; 200k+ alerts would take days to weeks unattended. *(Confidence: medium — no single primary benchmark for this exact GPU+model+quant combination was found; figure is a defensible range built from Qwen's own vendor benchmark plus consumer-GPU community data, not a direct measurement.)*
- **Sample, don't run the full corpus.** Given the latency math above, a stratified sample (by ATT&CK technique and event_type, sized for the confidence interval the eval harness needs) is required, not optional, for any four-agent design; a single-agent design relaxes but does not eliminate this constraint. *(Confidence: high given the latency numbers, though the eval harness's actual required sample size is out of scope here.)*
- **Cap effective per-request context well under Qwen2.5-7B's advertised 131K window — treat ~8K-16K tokens as the safe practical ceiling for this project, not the marketing number.** Ollama's own default `num_ctx` is only 4096 tokens on <24GB-VRAM hosts (this 8GB card included) unless explicitly overridden, and independent long-context evaluation shows Qwen2.5-7B's accuracy degrades sharply well before its nominal maximum. A 38-53-field alert record plus schema/instructions is unlikely to blow this budget per-call, but a Correlation agent that concatenates multiple prior alerts' full raw payloads could. *(Confidence: medium-high — the num_ctx default is primary-sourced and firm; the degradation-threshold figure comes from one arXiv paper not yet cross-checked against a second independent source.)*
- **Q4_K_M schema-compliance data is genuinely mixed for Qwen2.5-7B specifically and does not cleanly support "quantization degrades JSON adherence" as a universal rule** — one measured benchmark found Qwen2.5-7B Q4_K_M schema compliance (73.9%) *higher* than its own Q8_0 result (65.2%), the opposite of the pattern seen in Llama-3.1-8B and Mistral-7B in the same study. Do not assume quantization is a safe non-issue, but also do not assume Q8 is a guaranteed fix for this specific model family. *(Confidence: low-medium — single benchmark source, methodology not independently cross-verified, numerically counter-intuitive result flagged by the source itself as unexplained.)*

## Findings

### 1. Structured output on Ollama: current (2026) correct mechanism

**Ollama's `format` parameter, since v0.5.0 (released 2024-12-06), accepts a full JSON Schema and constrains decoding, not just retries on parse failure.** Primary confirmation: [Ollama's own 0.5 announcement](https://ollama.com/blog/structured-outputs) states the feature "makes it possible to constrain a model's output to a specific format defined by a JSON schema," explicitly framed as more reliable than plain "JSON mode." The underlying mechanism (per multiple 2026 technical write-ups, not contradicted by anything in Ollama's own docs) is that Ollama compiles the schema into a grammar and uses **XGrammar** to mask invalid tokens at each decoding step, so a schema-violating token is never sampled — this is decoding-time constraint, the same class of technique as llama.cpp's native GBNF grammars (Ollama is a llama.cpp wrapper). Ollama's own [Structured Outputs docs](https://docs.ollama.com/capabilities/structured-outputs) still recommend lowering temperature to 0 and validating with Pydantic/Zod after the fact — the vendor does not claim a semantic-correctness guarantee, only shape conformance. This matches and reconfirms Phase 0's Q3 finding (`phase-0-architecture.md:76-90`) as still accurate 12 months on (no version-breaking change found).

**Library comparison — which constrain decoding vs which retry:**

| Method | Constrains decoding? | Mechanism | Source |
|---|---|---|---|
| Ollama `format` (v0.5+) | **Yes** | JSON Schema → grammar → XGrammar token masking | [ollama.com/blog/structured-outputs](https://ollama.com/blog/structured-outputs), [docs.ollama.com/capabilities/structured-outputs](https://docs.ollama.com/capabilities/structured-outputs) |
| llama.cpp GBNF grammars | **Yes** | Same class of technique, more general (full CFG, not just JSON Schema); Ollama's engine is built on this | [llama.cpp grammars docs](https://github.com/ggml-org/llama.cpp/tree/master/grammars) (cited in Phase 0, unchanged) |
| Outlines (dottxt-ai) | **Yes** | FSM/grammar-based constrained generation, framework-level, model-agnostic | [github.com/dottxt-ai/outlines](https://github.com/dottxt-ai/outlines) |
| vLLM guided decoding | **Yes** | xgrammar/guidance backends, same class | [docs.vllm.ai structured-outputs](https://docs.vllm.ai/en/latest/features/structured_outputs.html) |
| **Instructor** | **No** | Confirmed this pass directly from Instructor's own Ollama integration doc: it wraps Ollama's OpenAI-compatible JSON mode and layers `max_retries`-based backoff, re-prompting with the Pydantic validation error on failure. It is a **retry loop with validation**, not a decoding-time constraint | [python.useinstructor.com/integrations/ollama](https://python.useinstructor.com/integrations/ollama/) |
| Plain prompted JSON | No | No enforcement at all | — |

This reconfirms, not contradicts, Phase 0's Q3 table — Instructor is retry-only, grammar methods are decoding-time. New this pass: an open Ollama GitHub issue (found via search, not independently fetched/verified) reportedly describes schema-adherence problems specific to the Qwen 3.5/3.6 model series as of April 2026 — **not verified against the actual GitHub issue text**, and Qwen2.5 (this project's model) is a different, older generation; flagged as an open item, not applied to this project's model choice.

### 2. Does 7B @ Q4_K_M reliably produce schema-valid output?

**Mixed, model-family-dependent — not a clean "quantization degrades JSON" story for Qwen2.5-7B specifically.** The most directly relevant measured source found is an [AscentCore 2026 benchmark](https://ascentcore.com/2026/04/01/small-llm-performance-benchmark/) evaluating 22 quantized configs across 11 models (1B-14B) on JSON parse rate and schema compliance:

| Model | Q4_K_M parse / schema compliance | Q8_0 parse / schema compliance |
|---|---|---|
| Qwen2.5-7B | 95.7% / **73.9%** | 95.7% / **65.2%** |
| Llama-3.1-8B | 91.3% / 91.3% | 100% / 95.7% |
| Mistral-7B | 95.7% / 39.1% | 100% / 47.8% |

Qwen2.5-7B's schema compliance is *higher* at Q4_K_M than Q8_0 in this benchmark — the opposite direction from Llama-3.1-8B and Mistral-7B in the same study, which the source itself flags as unexplained ("quantization impact varies by model family"). **Caveat on this finding: it is a single benchmark, not independently cross-verified against a second source in this pass, and the exact schema-complexity/prompt setup wasn't fully re-derived.** A separate, much smaller/weaker model (SmolLM2 1.7B) showed catastrophic Q4_K_M degradation (26.1% parse rate) in a different source surfaced by search but not fetched to primary text — this is consistent with a "quantization hurts smaller/weaker models more than mid-size ones" pattern, but that pattern is inferred, not directly measured across a controlled model-size sweep in one study.

Two implications for this project: (a) the schema-compliance numbers above (65-74%) are for *unconstrained* prompted JSON in that benchmark's setup, most likely — this project should still expect Ollama's grammar-constrained `format` to push structural validity much closer to 100% regardless of quantization, per the decoding-constraint mechanism in Q1, since the model literally cannot sample an invalid token; and (b) even with grammar constraint on shape, *semantic* correctness (right enum value, valid MITRE technique ID, not-hallucinated field content) is exactly the residual risk Phase 0 already flagged and is quantization-sensitive in a way the AscentCore numbers hint at but don't isolate.

### 3. Is four-agent decomposition justified, or cargo-culting?

**The honest answer, per measured evidence found this pass: for a classification-style task, a single well-prompted call is more likely to match or beat multi-agent decomposition, at substantially lower cost — this directly contradicts adopting the four-agent sketch without re-justifying it.**

Three separate measured comparisons found:

1. **[Stance detection (arXiv:2604.26319, "A Systematic Comparison of Prompting and Multi-Agent Methods for LLM-based Stance Detection")](https://arxiv.org/html/2604.26319)** — the closest task-shape match to alert triage (a classification task, not open-ended reasoning), tested across 4 datasets, 15 LLMs, 5 methods. **Best single-prompt method (Auto-CoT, 73.7% avg F1) beat the best agent-based method (COLA, 68.9% avg F1) by 4.8 points overall**, with per-model gaps up to 14.1 points (GPT-3.5-Turbo) favoring the prompt method — despite agent methods using **7-12x more API calls per sample**. This is a direct, measured, primary-source contradiction of "decompose into more agents for better classification accuracy."

2. **["When Single-Agent with Skills Replace Multi-Agent Systems and When They Fail" (arXiv:2601.04748)](https://arxiv.org/pdf/2601.04748)** — found single-agent-with-skills matches multi-agent accuracy on tasks manageable sequentially, at **54% lower token consumption and 50% lower latency**, but flags a genuine capacity-dependent caveat: **on *smaller* models specifically, single-agent-with-skills struggled to manage role-specific sub-prompts reliably, and multi-agent decomposition performed more consistently on the smallest models tested.** This is the one piece of evidence cutting the other way, and it matters directly here because Qwen2.5-7B is a small model by this literature's standard — it does not resolve to "single agent always wins," it resolves to "test both, don't assume."

3. **[Essay grading (arXiv:2601.22386, "Specialists or Generalists?")](https://arxiv.org/html/2601.22386v1)** — a QWK-scored classification/rating task: multi-agent beat single-agent by only 2.88 QWK points (0.7453 vs 0.7165, ~4% relative gain) for 4x the compute, and the advantage was **not uniform** — multi-agent had a large edge (up to 26.6 points) on the hardest/lowest-quality cases but single-agent was *better* on mid-range cases. The paper's own conclusion: architecture choice should be driven by which error mode matters most for the use case, not a blanket "more agents = better."

**Contrary/supporting context on failure modes:** [MAST (arXiv:2503.13657, "Why Do Multi-Agent LLM Systems Fail?")](https://arxiv.org/abs/2503.13657), already cited in Phase 0, analyzed 1600+ traces across 7 MAS frameworks (models tested included GPT-4, Claude 3, Qwen2.5, CodeLlama) and found 14 distinct failure modes across three categories — **system design issues, inter-agent misalignment, and task-verification failures** — meaning added agents are a new, non-trivial failure surface, not a free accuracy gain, independent of whether they help on any given task.

**Net read:** the four-agent sketch (Enrichment → Triage → Correlation → Critic) is not obviously wrong, but it is not evidence-backed as *better* than one strong single-call classifier either — no source found in this pass measured this exact decomposition on this exact task. Given (a) the classification-task evidence leaning toward single-prompt, (b) the small-model caveat leaning toward multi-agent, and (c) MAST's warning that decomposition adds failure surface regardless, **the defensible position is: build a strong single-agent baseline first, and justify each additional agent stage only if it measurably beats that baseline on the actual eval harness** — which also happens to make "rigorous eval harness as the differentiator" (per the task's own framing vs. zhadyz/AI_SOC and Elastic Alert Zero) the natural place this gets decided, rather than deciding it from a Phase 0 sketch.

### 4. Realistic per-alert latency under `OLLAMA_NUM_PARALLEL=1`, and sampling implications

**Confirmed primary-source: `OLLAMA_NUM_PARALLEL` defaults to 1, hardcoded, with no memory-based auto-scaling** — verified directly from Ollama's own source, `NumParallel = Uint("OLLAMA_NUM_PARALLEL", 1)` in [`envconfig/config.go`](https://github.com/ollama/ollama/blob/main/envconfig/config.go), and restated in prose on [docs.ollama.com/faq](https://docs.ollama.com/faq): "The maximum number of parallel requests each model will process at the same time, default 1." (Some secondary blog sources claim an "auto-select 4 or 1 based on memory" behavior — **not found in the primary source and treated as incorrect/outdated for this project's purposes**; the task's stated premise of effectively-sequential agents is confirmed correct.) This means 4 chained agent calls per alert are strictly serialized on this box — there is no concurrency benefit to be had by, e.g., firing Triage and a second alert's Enrichment simultaneously.

**Latency estimate (not a direct measurement — no single primary benchmark exists for this exact GPU+model+quant+framework combination):** Qwen's own vendor benchmark ([qwen.readthedocs.io speed_benchmark](https://qwen.readthedocs.io/en/v2.5/benchmark/speed_benchmark.html)) reports 7B-class generation in the 30-40 tok/s range on an A100 at moderate context via the plain Transformers path (vLLM is substantially faster but is the *rejected* runtime per Phase 0 Q1, not what this project runs). Community-reported consumer-GPU numbers for 7-8B Q4_K_M models cluster around 40-80 tok/s on 8GB-class cards, though none of these are a controlled, citable primary benchmark for an RTX 3080 specifically — this is aggregated community/blog data, flagged as such, not a vendor or paper claim. Grammar-constrained decoding (Q1/Q2 above) adds some per-token masking overhead, magnitude not quantified in any source fetched.

Working estimate for this project, stated as a range with the uncertainty explicit: at ~20-40 tok/s decode and a few hundred tokens of prompt-processing + generation per agent call (structured JSON output is comparatively short, but prompt processing of a 38-53-field alert plus schema/instructions is not trivial), a single agent call is plausibly **2-8 seconds**; a 4-agent sequential chain is plausibly **~10-35 seconds per alert**, before retry overhead from schema-validation failures (Phase 0's own recommended 2-3 bounded retries would multiply the affected fraction of alerts further).

**Implication for corpus-scale evaluation:** the corpus is 202,845 malicious events at a stated 4:1 benign ratio (per `src/corpus.py::assemble_corpus`), i.e. on the order of ~1M total records if fully assembled, though the actual working/eval subset size is a separate, unread decision (out of scope here — eval harness sizing is a different brief). Even taking a much smaller "thousands of alerts" framing at face value: 5,000 alerts x 15 seconds/alert (midpoint estimate) = ~21 hours of unattended sequential GPU time for a four-agent pipeline; the full malicious-only corpus at that rate would be roughly 5 weeks of continuous unattended runtime. **This makes full-corpus evaluation schedule-infeasible on this hardware regardless of agent count, and stratified sampling (by ATT&CK technique, per `AlertRecord.attack_technique`/`attack_tactics`, and by `event_type`) is a hard requirement, not a nice-to-have** — this is new ground relative to Phase 0/Phase 1, which never modeled per-alert LLM latency against corpus size.

### 5. Token-budget / context-window constraints for 38-53-field alert records

**Qwen2.5-7B-Instruct's advertised context is 131,072 input / 8,192 output tokens** per its own [Hugging Face model card](https://huggingface.co/Qwen/Qwen2.5-7B-Instruct) — but two separate constraints cut this down hard in practice:

1. **The model's own default config caps at 32,768 tokens without YaRN scaling** — the 131K figure requires adding an explicit `rope_scaling`/YaRN block to `config.json` (per the model card), which is a GGUF/llama.cpp-path complication not confirmed to be pre-applied in standard Ollama-pulled GGUF builds of this model (not independently verified this pass — flagged as an open item).
2. **Ollama's own runtime default `num_ctx` is far smaller still — 4k tokens on any host with <24GiB VRAM**, per [docs.ollama.com/context-length](https://docs.ollama.com/context-length) (this project's 8GB RTX 3080 falls in that bracket), overridable via `OLLAMA_CONTEXT_LENGTH` or a per-request `num_ctx` option, but **not raised automatically** — a silent default this project must explicitly override if any agent's prompt exceeds ~4K tokens, or requests will be silently truncated rather than erroring.

Separately, **measured long-context degradation for Qwen2.5-7B specifically** (not vendor-claimed): one arXiv paper ([arXiv:2601.15300, "Intelligence Degradation in Long-Context LLMs"](https://arxiv.org/html/2601.15300v1)) measured a sharp accuracy cliff — F1 dropping from 0.556 to 0.302 (45.5% relative drop) — at roughly 43% of the model's stated 131K maximum (≈55K tokens), on NarrativeQA-style long-document QA. **This is a single source, not cross-checked against a second independent long-context benchmark this pass**, and the task type (long narrative QA) is not the same shape as a flat 38-53-field structured alert record, so the specific threshold should not be over-applied — but it is directional confirmation that "the model supports 131K" and "the model performs well at 131K" are different claims, consistent with the broader "lost in the middle" literature.

**Practical read for this project:** a single `AlertRecord` (38-53 fields, including the lossless `raw_event` dict) plus a JSON-Schema definition and task instructions is very unlikely to approach even the 4K default on its own — this is not the binding constraint for a single-alert Triage/Enrichment call. It **becomes** the binding constraint the moment any agent (most plausibly the sketched "Correlation" agent, which by design needs multiple prior alerts' context) concatenates several full `raw_event` payloads into one prompt — that is exactly the design that needs an explicit `num_ctx` override and a stated, tested token budget, not the default.

## Corrections to prior assumptions

This section is not empty — three concrete corrections/refinements to the Phase 0 brief and the four-agent sketch:

1. **The four-agent decomposition is not evidence-justified as-is, and this brief found direct measured evidence Phase 0 did not have or cite.** Phase 0's Q4 section (`phase-0-architecture.md:94-115`) justified *sequential* over *supervisor/blackboard* orchestration patterns well, but never asked or answered "is decomposing into 4 agents better than 1 well-prompted agent for *this classification task*" — it assumed the 4-agent count as given and only reasoned about how to wire them together. This pass found three papers that directly measured single-prompt vs. multi-agent on classification/rating tasks (stance detection, essay grading, general single-vs-multi-agent-with-skills), and the weight of that evidence (especially the stance-detection paper, the closest task-shape match) favors starting from a single-agent baseline, not assuming four agents are correct. This is the single most load-bearing correction in this brief.

2. **Phase 0's "documented-and-confirmed" flag on Ollama's structured-output mechanism holds up, but the small-model/quantization interaction is murkier than Phase 0 implied.** Phase 0 (`phase-0-architecture.md:90`) stated the structural-vs-semantic-guarantee distinction was "the single most important nuance" and "solid" — that remains true and is reconfirmed here. But Phase 0 did not investigate whether Q4_K_M quantization itself measurably degrades schema adherence before grammar constraint is even applied; this pass found that evidence exists, is mixed and counter-intuitive for Qwen2.5-7B specifically (Q4_K_M *outperforming* Q8_0 in one benchmark), and should not be assumed away.

3. **A genuinely new, previously-unexamined hard constraint: `OLLAMA_NUM_PARALLEL=1` plus realistic per-call latency makes full-corpus evaluation infeasible and forces explicit stratified sampling.** Phase 0 flagged latency as "a concern" in the abstract (`phase-0-architecture.md:124`, citing Anthropic's ~15x token-use warning for multi-agent systems generically) but never modeled it against this project's actual corpus size (202,845+ malicious events) or Ollama's concrete concurrency ceiling. This brief is the first to connect those numbers and conclude sampling is mandatory, not a possible later optimization.

Everything else checked this pass (Ollama's `format`-param mechanism being decoding-time not retry-based, Instructor being retry-only, MAST's failure taxonomy, the general "structural not semantic guarantee" framing, the choice of hand-rolled orchestration over LangGraph/CrewAI) **reconfirmed rather than contradicted** Phase 0 — those sections of Phase 0 remain accurate as of this research date and did not need correction.

## Open questions

- **No single controlled benchmark exists (found in this pass) for Qwen2.5-7B-Instruct Q4_K_M tokens/sec on an RTX 3080 specifically via Ollama.** The latency estimate in Finding 4 is built from Qwen's own A100/Transformers vendor numbers plus aggregated consumer-GPU community reports, not a directly reproducible primary measurement for this project's exact hardware/runtime combination. **Recommended next step: a short, real, on-hardware timing script (a handful of representative alerts through the actual planned agent count) would resolve this in minutes and should be done before finalizing any sampling-rate decision** — this is squarely a "verify blocking assumption via a real measurement" case, not something further research alone can resolve.
- **Whether Ollama's pulled/quantized Qwen2.5-7B GGUF build ships with YaRN scaling pre-applied for >32K contexts** — not independently verified; matters only if a Correlation-style agent design is kept and needs long context.
- **The exact schema-complexity and prompting setup behind the AscentCore Q4_K_M/Q8_0 schema-compliance numbers** (Finding 2) — the benchmark's own methodology page was fetched only at summary level; the counter-intuitive Qwen2.5-7B result (Q4 beating Q8) was not independently cross-checked against a second source and could be a benchmark-specific artifact.
- **The reported Ollama GitHub issue about Qwen 3.5/3.6 schema-adherence problems** (Finding 1) — surfaced only via search snippet, not fetched/confirmed directly, and concerns a different model generation than this project uses; not applied to any recommendation here.
- **Whether a genuinely single-agent design would need a different prompting strategy (e.g., chain-of-thought before the final JSON block) to hit both good classification accuracy and clean schema conformance in one call** — this is a design/implementation question properly belonging to whichever agent builds Phase 2, not resolved by this research-only brief per the scope boundary.
